## 프로젝트 목표와 범위

**참고 페이지:** 명세서 p.3~6, 수업 자료 p.4~5

이번 작업은 **기존 EnjoyTrip 웹 화면에 Servlet·JSP 기반의 백엔드를 연결하는 Web(Backend) 5회차 프로젝트**다. 관광정보를 화면에 보여 주는 기능과 회원 기능을 실제 요청·처리·응답으로 연결하고, MVC 구조에 맞게 역할을 나누는 것이 목표다.

| 항목 | 명세서 기준 |
|---|---|
| 진행일자 | 2026.10.30 |
| 예상 구현 시간 | 필수 기능 5시간, 추가 기능 2시간, 심화 기능 1시간 |
| 사용 기술·도구 | Servlet, JSP, HTML/CSS/JavaScript, STS, VS Code, Tomcat, MySQL |
| 기존 작업과의 연결 | 지난 관통 프로젝트의 웹 페이지를 바탕으로 백엔드 구현 |
| 최종 반영 위치 | GitLab; 제출 방식은 반별로 다를 수 있음 |

예상 시간은 구현 규모를 가늠하는 기준이며 제출 시각을 의미하지 않는다. 두 PDF에는 구체적인 마감 시각이 제시되어 있지 않다.

**EnjoyTrip 명세서는 완성할 서비스의 범위를, 수업 자료는 회원 기능을 구현하는 방법을 보여 준다.** 이메일 중복 검사와 회원 목록 페이징 예제를 완료했다고 관광정보 조회나 비밀번호 찾기까지 완료되는 것은 아니다.

## 요구사항과 설계

**참고 페이지:** 명세서 p.4~6, 수업 자료 p.4~5

### 작업 순서

1. 필수 기능을 확인하고 팀의 요구사항 목록을 정리한다.
2. Usecase Diagram으로 사용자·관리자가 수행할 기능을 분석한다.
3. MVC 구조에 맞춰 클래스를 설계한다.
4. 기존 화면에 Servlet·JSP 처리를 연결한다.
5. 구현 결과를 확인하고 문서·캡처·소스코드를 Git에 반영한다.

Usecase Diagram은 메인 관광정보 검색, 여행 계획 관리, 회원·로그인 관리, 공지사항 등의 사용자 동작을 표현한다. Class Diagram은 이 기능을 어떤 클래스와 연결 관계로 구현할지 나타낸다. 문서의 예시를 그대로 두기보다 **실제로 구현한 기능과 구조에 맞게 개선**해야 한다.

### MVC 역할 분담

| 구성 | 구현 중 맡길 작업 |
|---|---|
| Controller — Servlet | 요청 파라미터 확인, Service 호출, 결과에 따른 JSP 이동 또는 데이터 응답 |
| Service | 기능의 처리 흐름과 업무 처리 |
| DAO | 데이터 조회·변경에 대한 접근 |
| DTO·데이터 객체 | 계층 사이에 전달할 데이터 표현 |
| View — JSP | 처리 결과를 화면에 표시 |

일반 화면 요청은 Servlet에서 처리한 결과를 JSP로 전달하고, 이메일 중복 검사처럼 화면 일부의 상태만 바꾸는 요청은 JSON으로 응답한다. 모든 요청을 동일하게 JSP로 이동시키면 Ajax 코드가 기대하는 JSON을 받을 수 없으므로 응답 형태를 구분한다.

수업 자료는 **Servlet Controller와 HTML → JSP 전환을 통한 MPA 화면 구성**을 강조한다. 전체 로드맵에 표시된 Spring·Vue·REST 구조를 이번 단계의 필수 구현 방식으로 확대하지 않는다.

## 이메일 중복 검사

**참고 페이지:** 수업 자료 p.9~11 · TODO 01~05

### 요청·응답 흐름

회원가입 화면의 이메일 `input` 이벤트에서 중복 확인 요청을 보내고, 응답의 `canUse`에 따라 입력창 상태를 변경한다.

`이메일 입력 → /member?action=email-check&email=입력값 → 중복 확인 → JSON 응답 → 입력창 상태 변경`

| 값·설정 | 의미 |
|---|---|
| `canUse: true` | 사용 가능한 이메일 |
| `canUse: false` | 이미 사용 중인 이메일 |
| `is-valid` | 사용 가능 상태 표시 |
| `is-invalid` | 사용 불가 상태 표시 |
| `invalid-feedback` | 사용 불가 안내 문구 |

유효 상태가 바뀔 때는 새 상태의 클래스를 추가하면서 반대 상태의 클래스를 제거한다. 두 클래스가 함께 남지 않는지 확인한다.

### JSON 응답

제공 프로젝트의 Jackson 의존성을 확인하고 ObjectMapper로 객체를 JSON 문자열로 변환한다. 다음은 원본 `toJSON()` 내부의 핵심 발췌다.

```java
String json = new ObjectMapper().writeValueAsString(target);
response.setContentType("application/json;charset=utf-8");
response.getWriter().write(json);
```

클라이언트는 `response.json()`으로 이 응답을 읽는다. 회원가입 JSP의 HTML이 반환되지 않는지, 속성 이름이 `canUse`로 일치하는지, 한글 안내와 JSON 인코딩이 정상인지 확인한다. 화면의 상태 표시는 Bootstrap의 [폼 검증 방식](https://getbootstrap.com/docs/5.3/forms/validation/#server-side)을 참고한다.

## 검색과 페이징

**참고 페이지:** 수업 자료 p.13~21 · TODO 06~12

### 검색 조건과 결과 정보

페이지 이동은 단순히 번호를 바꾸는 작업이 아니다. **현재 검색 조건을 유지한 상태에서 해당 페이지의 데이터와 이동 정보를 다시 구해야 한다.**

| 객체·필드 | 역할 |
|---|---|
| `SearchCondition.key` | 검색 항목; `name` 또는 `email` |
| `SearchCondition.word` | 검색어 |
| `SearchCondition.currentPage` | 현재 페이지 |
| `SearchCondition.itemsPerPage` | 페이지당 데이터 수 |
| `Page.condition` | 현재 검색 조건 |
| `Page.totalItems` | 검색 조건에 맞는 전체 항목 수 |
| `Page.list` | 현재 페이지에 보여 줄 데이터 |
| `Page.totalPages` | 전체 페이지 수 |
| `Page.navSize` | 한 번에 표시할 페이지 번호 수; 예시는 5 |
| `Page.startPage`, `endPage` | 현재 내비게이션의 시작·끝 번호 |
| `Page.hasPre`, `hasNext` | 이전·다음 페이지 묶음 표시 여부 |

`itemsPerPage`와 `navSize`는 다르다. 전자는 한 페이지의 회원 수이고, 후자는 화면에 나열할 페이지 번호 수다. `Page`의 모든 필드를 데이터 저장소에서 조회하는 것이 아니라 전체 건수와 목록을 바탕으로 화면용 정보를 구성한다.

### 건수 계산과 목록 추출

수업 예시는 이름·이메일에 `contains(word)`를 적용하고, 검색어가 없으면 모든 회원을 통과시킨다. 잘못된 검색 항목은 일치하지 않는 것으로 처리한다.

**전체 건수와 현재 페이지 목록에 동일한 검색 조건을 적용**해야 한다. 건수를 전체 회원 수로 계산하면서 목록만 검색하면 페이지 수와 실제 결과가 맞지 않는다.

다음은 원본 목록 처리에서 필터링·범위 추출 부분만 발췌했다.

```java
members.stream()
    .filter(member -> matchesCondition(member, condition))
    .skip(condition.getItemsPerPage() * (condition.getCurrentPage() - 1))
    .limit(condition.getItemsPerPage())
    .collect(Collectors.toList());
```

페이지당 5명이고 현재 페이지가 3이면 앞의 10명을 건너뛰고 최대 5명을 가져온다. `getTotalCount(condition)`는 페이지로 자르기 전의 일치 건수를 세어야 한다.

이 코드는 **메모리의 회원 목록을 Stream으로 처리하는 예시**다. 명세서의 DB 도식과 구분하여 읽고, 이번 프로젝트의 데이터 접근 구현은 제공 코드와 팀 설계에 맞춘다.

### 화면 진입과 페이지 이동

| 동작 | 검색 조건 | 현재 페이지 |
|---|---|---|
| 상단의 회원 목록 링크로 처음 진입 | 없음 | 기본값 1 |
| 검색 폼으로 새 검색 | 새로 입력한 key·word 적용 | 1로 초기화 |
| 페이지 번호 클릭 | 기존 key·word 유지 | 클릭한 번호 |
| 이전·다음 묶음 클릭 | 기존 key·word 유지 | 각각 startPage - 1, endPage + 1 |

검색 폼에는 `action=member-list`, `currentPage`, `key`, `word`를 전달할 수 있도록 구성한다. 새 검색은 1페이지에서 시작하고, 페이지 이동은 같은 폼의 숨겨진 `currentPage`만 바꿔 제출한다.

다음은 원본 페이지 링크 클릭 처리의 핵심 발췌다. 이벤트 등록과 반복문은 생략했다.

```javascript
e.preventDefault();
document.querySelector("#currentPage").value = link.dataset.page;
document.querySelector("#search-form").submit();
```

JSP는 `page.hasPre`·`page.hasNext`로 이동 버튼을 표시하고, `page.startPage`부터 `page.endPage`까지 번호를 만든다. 현재 번호에는 활성 상태를 표시한다. 화면은 [Bootstrap Pagination](https://getbootstrap.com/docs/5.3/components/pagination/)을 참고한다.

## 회원 상세·수정·삭제

**참고 페이지:** 명세서 p.11~12, 수업 자료 p.23~25 · TODO 13~20

### 상세와 권한

회원 목록의 이메일을 클릭하면 해당 회원의 상세 정보로 이동한다. 수업 예시의 요청은 `/auth?action=member-detail&email=...`이다.

상세 화면의 수정·삭제 버튼은 **관리자 또는 로그인한 본인**일 때 표시한다. 화면 표시 조건과 실제 수정·삭제 요청을 처리하는 권한 기준이 맞는지 함께 확인한다. 일반 사용자와 관리자 화면을 각각 확인해야 한다.

### 수정과 세션 갱신

회원 데이터를 수정한 뒤 상세 화면으로 Redirect한다. 로그인한 본인이 수정한 경우에는 저장된 회원 정보뿐 아니라 세션의 `loginUser`도 갱신해야 헤더 이름 등이 새 값으로 표시된다.

다음은 원본의 본인 수정 후 세션 갱신 부분이다. `modified` 생성과 Service 호출은 생략했다.

```java
HttpSession session = request.getSession();
if (session.getAttribute("loginUser") instanceof Member m
        && m.getEmail().equals(email)) {
    session.setAttribute("loginUser", modified);
}
```

다른 회원을 수정했을 때 현재 관리자의 `loginUser`까지 수정 대상 회원으로 바뀌지 않는지 확인한다.

### 삭제와 로그아웃

삭제 대상에 따라 후속 처리를 구분한다.

| 삭제 상황 | 수업 예시의 후속 처리 |
|---|---|
| 로그인한 본인 삭제 | `session.invalidate()`로 로그아웃 후 홈으로 Redirect |
| 다른 회원 삭제 | 삭제 완료 `alertMsg`를 저장하고 회원 목록 1페이지로 Redirect |

회원 데이터가 삭제되어도 세션이 그대로 남으면 탈퇴한 사용자가 로그인 상태처럼 보일 수 있다. 본인 탈퇴 후에는 헤더와 로그인 상태까지 함께 확인한다.
